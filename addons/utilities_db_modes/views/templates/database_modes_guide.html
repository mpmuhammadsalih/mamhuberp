Database modes: single-DB vs multi-DB

This app can use one Oracle database for everything, or a separate auth database for logins and tenant_databases, with per-tenant business databases. This page summarizes how that works in config/settings.py and db.py, and what to put in .env.

Current process (read-only)
Multi-DB mode (app flag): {% if is_multi_db_mode %}ON{% else %}OFF{% endif %}  —  On when both AUTH_DB_USERNAME and AUTH_DB_DSN are set, unless overridden by MULTI_DB_MODE=single (or 0 / false). Main DB configured: {{ 'yes' if main_user_set and main_dsn_set else 'no' }}. Auth credentials set: {{ 'yes' if auth_user_set and auth_dsn_set else 'no' }}.

How the app decides

Optionally set MULTI_DB_MODE in .env: single (or 0) forces single-DB even if AUTH_DB_* variables are still present; restart the server after saving.

With no override, is_multi_db_mode() is true only when both AUTH_DB_USERNAME and AUTH_DB_DSN are set (non-empty). Then logins and tables such as login_users, roles, and tenant_databases are read via the auth connection when the code path uses _get_connection_auth() in multi-DB mode.

The main business connection uses DB_USERNAME, DB_PASSWORD, and DB_DSN when you are not routing the request to a specific tenant connection.

Single-DB mode (one physical Oracle)

Use this when all schemas and app tables live on one database (typical dev / small deployment).

  • Set DB_USERNAME, DB_PASSWORD, DB_DSN to your Oracle user and Easy Connect string (e.g. host:1521/service_name).
  • Leave AUTH_DB_USERNAME and AUTH_DB_DSN empty if you want is_multi_db_mode() to stay false.
  • Some features (for example HO APIs that call _get_tenant_connection('HO')) load tenant connection details from tenant_databases using _get_auth_connection(), which requires AUTH_DB_* to be set. If you see errors about the auth database not being configured, either:
    • set AUTH_DB_USERNAME, AUTH_DB_PASSWORD, AUTH_DB_DSN to the same values as DB_* (one physical DB, two env blocks), or
    • change application code to read tenant_databases via the default connection when not in multi-DB mode (developer change).
  • Ensure a row exists in tenant_databases for head office: tenant_id = 'HO', with active_flag not disabling the row (NVL(active_flag,'Y') = 'Y'), and ip / port / service_name matching your database. Otherwise APIs such as customer_request_pending_count raise Tenant 'HO' not found or inactive.

Example .env (single physical DB, auth vars aligned with main DB)

# Main app database
DB_USERNAME=app_user
DB_PASSWORD=secret
DB_DSN=192.168.1.10:1521/ORCL

# Same database — satisfies _get_auth_connection() and tenant_databases lookups
AUTH_DB_USERNAME=app_user
AUTH_DB_PASSWORD=secret
AUTH_DB_DSN=192.168.1.10:1521/ORCL

Multi-DB mode (separate auth DB + tenant DBs)

Use this when login_users, roles, and tenant_databases live on a central Oracle instance, and each tenant’s business data is on its own database (or service) defined by rows in tenant_databases.

  • Set AUTH_DB_USERNAME, AUTH_DB_PASSWORD, AUTH_DB_DSN to the central auth database.
  • Keep DB_* as a default / fallback user where the code falls back (for example when a tenant row omits a username).
  • Each active row in tenant_databases supplies ip, port, service_name, and optional username / password for that tenant’s connection.
  • Head office still needs tenant_id = 'HO' if features use _get_tenant_connection('HO').

Example .env (multi-DB)

# Central auth / registry
AUTH_DB_USERNAME=central_user
AUTH_DB_PASSWORD=central_pass
AUTH_DB_DSN=10.0.0.1:1521/AUTHSRV

# Default Oracle user (fallback when tenant row has no username)
DB_USERNAME=rfim_user
DB_PASSWORD=rfim_pass
DB_DSN=192.168.1.50:1521/TENANT_DEFAULT

Rules of thumb

  • Auth tables (login_users, roles, role_permissions, tenant_databases) must be queried with the auth connection pattern in code; in multi-DB mode that is the auth DB.
  • Business tables use the tenant (or default) connection per session.
  • After changing .env, restart the application process.
  • Avoid duplicate keys in .env (e.g. two AUTH_DB_USERNAME lines); the loader may use the last value and confuse debugging.
